# OHVC Trouble Shooting Procedure - MML SOP

當 OHVC 發生異常時，應依序進入以下 8 個階段進行排查與復歸。只有在前一階段確認無法解除異常時，才允許進入下一階段。

## 階段 1: Change Rollback (變更回退)
- **目標**：確認是否因近期系統變更導致異常。
- **判斷邏輯**：
  1. 檢查「後調成功目」異常是否解除？
     - 成功解除 ➡️ 【排查結束】。
     - 未解除 ➡️ 繼續。
  2. 確認「是否有 Change」？
     - 若無 Change ➡️ 進入【階段 2: OHT 復歸】。
     - 若有 Change ➡️ 執行 Rollback 並檢查是否解除。
  3. *特殊情況處理*：如果有 Change，需依時間順序評估 Rollback：確認有無 `Map Switch`、有無 `Takeover` 或是 `Large Scale` 變更。
  4. 執行完上述 Rollback 後，再次確認異常是否解除：
     - 解除 ➡️ 【排查結束】。
     - 未解除 ➡️ 進入【階段 2: OHT 復歸】。

## 階段 2: OHT 復歸 (OHT Recovery)
- **目標**：排除 OHT 車輛端的硬體或訊號異常。
- **判斷邏輯**：
  1. 檢查是否為「單一車輛 (VHL)」異常？
     - 若為單一車輛 ➡️ 執行 `2.1 VHL 手動復歸`。
     - 若不是 ➡️ 進入【階段 3: 通訊修復】。
  2. VHL 手動復歸後，異常是否解除？
     - 解除 ➡️ 【排查結束】。
     - 未解除 ➡️ 檢查是否為「PSP 燈號異常」？
  3. 依據 PSP 燈號狀態：
     - 若為 PSP 異常 ➡️ 執行 `2.2 PSP 異常處理`。
     - 若非 PSP 異常 ➡️ 執行 `2.3 BC/BM T/S`。
  4. 執行完 2.2 或 2.3 後，進入【階段 3: 通訊修復】。

## 階段 3: 通訊修復 (Communication Recovery)
- **目標**：解決網路或通訊協定層級的斷聯。
- **判斷邏輯**：
  1. 檢查 OHT 通訊是否異常？
     - 若異常 ➡️ 進行現場硬體確認與修復。
     - 若無異常 ➡️ 進入【階段 4: MSG Handle】。
  2. 通訊修復後，異常是否解除？
     - 解除 ➡️ 【排查結束】。
     - 未解除 ➡️ 進入【階段 4: MSG Handle】。

## 階段 4: MSG Handle (訊息處理)
- **目標**：處理訊息隊列 (Queue) 積壓或錯誤。
- **判斷邏輯**：
  1. 檢查 Master MSG Q 是否積壓？
     - 無積壓 ➡️ 進入【階段 5: 架構確認】。
     - 有積壓 ➡️ 確認是「單一 Module」還是「多個全局」異常？
  2. 依據影響範圍處置：
     - 單一 Module 異常 ➡️ 進行 `單一 MOHVC 復歸` 並執行 `MSG SOP`。
     - 多個/全局異常 ➡️ 執行 `ML 阻礙 MSG 排除`。
  3. 執行後，異常是否解除？
     - 解除 ➡️ 【排查結束】。
     - 未解除 ➡️ 進入【階段 5: 架構確認】。

## 階段 5: 架構確認 (Architecture Confirmation)
- **目標**：確保系統控制權架構正確。
- **判斷邏輯**：
  1. 檢查是否為 Centralized OHVC (集中式控制)？
     - 若不是 ➡️ 進入【階段 6: 網卡切換與網路檢查】。
     - 若是 ➡️ 執行 `OHVC Manager 點檢`。
  2. 點檢後，異常是否解除？
     - 解除 ➡️ 【排查結束】。
     - 未解除 ➡️ 執行 `Takeover` (接管程序)。
  3. Takeover 後異常是否解除？
     - 解除 ➡️ 【排查結束】。
     - 未解除 ➡️ 進入【階段 6: 網卡切換與網路檢查】。

## 階段 6: 網卡切換與網路檢查 (NIC Switch & Network Check)
- **目標**：排除伺服器網卡或實體線路故障。
- **判斷邏輯**：
  1. 執行 `網卡切換` 動作。
  2. 進行 `PC 更換 Check` (伺服器檢查)。
  3. 評估是否需要進行「PC 更換」？
     - 需要 ➡️ 進行 PC 更換。
     - 不需要 ➡️ 解除並安排網卡/網路查修。
  4. 處置後異常是否解除？
     - 解除 ➡️ 【排查結束】。
     - 未解除 ➡️ 進入【階段 7: OHVC 切換】。

## 階段 7: OHVC 切換 (OHVC Switchover)
- **目標**：執行主從切換 (Switchover) 以排除環境因素。
- **判斷邏輯**：
  1. 執行 `OHVC 切換` 動作。
  2. 異常是否解除？
     - 解除 ➡️ 【排查結束】。
     - 未解除 ➡️ 尋求 `MML` & 跨廠專家支援。
  3. 設定系統為 `ONVC LOGOUT Batch` 進入【階段 8: 系統重啟】。

## 階段 8: 系統重啟 (System Reboot)
- **目標**：最後手段，透過重啟恢復初始狀態。
- **動作**：執行系統重啟。

# 📖 【詳細操作指引清單 (操作/畫面查閱指南)】
*(AI 提示：當工程師不知道如何執行某個階段的指令或不清楚要在哪裡看畫面時，請列出對應的說明給他。如果沒有記載，可以請專家確認。)*

## 🛠️ [階段 1] 怎麼確認 Change 或是執行 Rollback？
- **畫面位置**：`Deployment Portal` (系統部署中控台)
- **操作方式**：
  1. 在畫面上方查看 `Recent Changes` (近期變更紀錄)。
  2. 若確認要退版，點選目標版本的 `Rollback` 按紐。
  3. 若涉及圖資 (Map) 更新問題，請選擇 `Map Rollback` 頁籤。

## 🛠️ [階段 2] 2.1 VHL 手動復歸 怎麼做？
- **畫面位置**：`MCS Client` -> `Vehicle Monitor` (車輛監控介面)
- **操作方式**：
  1. 在列表找到異常的 OHT 車號。
  2. 點選右鍵 -> 選擇 `Force Cancel` 取消當前派車任務。
  3. 嘗試將車輛狀態切換為 `Auto`。若依舊異常，請聯絡現場維護工程師。

## 🛠️ [階段 4] 怎麼檢查 Master MSG Q 是否積壓？
- **畫面位置**：`OHVC Dashboard` (中控監控面板) -> 左側導覽列 `Message Queue Status`。
- **判斷方式**：
  - 查看 `Master Queue Size` 圖表。
  - 若數值變成紅色且直線攀升，代表訊息因某種原因被卡住 (積壓)。
  - 下方列表中會顯示是哪一個特定 Module 無法消化訊息。

## 🛠️ [階段 6] 網卡切換 怎麼操作？
- **畫面位置**：發生異常伺服器的作業系統網路設定。
- **操作方式**：
  1. 遠端登入目標 Server。
  2. 將 Primary NIC (主要網卡) 狀態設為 `Disable` (停用)。
  3. 系統通常會自動將路由切到 Secondary NIC (備援網卡)，請觀察是否有恢復連線。

## 🛠️ [階段 7] OHVC Switchover 如何執行？
- **畫面位置**：`OHVC Admin Console` (命令提示字元或系統後台終端機)。
- **操作方式**：
  1. 確認目前是哪一台擔任 Active 節點。
  2. 輸入指令 `ohvc_admin switchover master`。
  3. 等待約 5~10 秒讓備援機接管 Active 權限，並確認新節點的 Heartbeat 正常運作。
